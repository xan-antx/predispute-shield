# Failures

## Ring personas inflated to 23% of the dataset
**When:** day 1, first full run of `simulator.py`
**Symptom:** persona mix in `data/alerts.csv` came out honest 62.2%, ring 23.3%, opportunist 14.5% against a target of 75/20/5. Ring was over-represented 4.7x and opportunist was starved.
**Root cause:** the customer pool was built by drawing one persona per loop iteration with `random.choices(PERSONAS, weights=(0.75, 0.20, 0.05))`, then appending. But a ring draw does not append one account, it appends a whole cluster of 3-6 siblings sharing a device and address. So 5% of *draws* became roughly 22% of *accounts* (mean cluster size 4.5), and since alerts sample uniformly from the pool, the row-level mix inherited the same skew.
**Fix:** build the pool by count instead of by weighted draw — `round(0.75 * n)` honest, `round(0.20 * n)` opportunist, then mint ring clusters until the ring account count reaches `round(0.05 * n)`. Added a shuffle before assigning `customer_id` so the id itself carries no persona signal, and an assert in `main()` pinning the observed mix to the target.
**Result:** honest 74.9%, ring 4.9%, opportunist 20.2%. Ring cluster sizes still land at 3-6 accounts per shared device. Overall win rate moved 49.4% -> 52.0% and per-persona win rates to 55/44/42, all still inside the no-leakage band.

## Rupee sign crashed the console on Windows
**When:** day 3, first run of `evaluate.py`
**Symptom:** `UnicodeEncodeError: 'charmap' codec can't encode character '₹' in position 353`. The traceback pointed at `print(report)`, not at the file write — and `results.md` on disk was complete and correct, which made the failure look stranger than it was.
**Root cause:** the markdown table uses `₹` in its column headers. `RESULTS.write_text(..., encoding="utf-8")` handled that fine, but `print()` encodes through `sys.stdout`, which on Windows defaults to the console codepage (cp1252). cp1252 has no rupee sign, so the encode raised. Nothing to do with pandas or the report contents — purely the output stream.
**Fix:** `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` before printing, with `errors="replace"` so an exotic terminal degrades to `?` instead of taking the harness down. The file write needed no change; it was already explicitly UTF-8.
**Result:** table prints and writes identically. Worth remembering for `dashboard.py` and any evidence-packet output — every rupee amount this project prints is a latent instance of the same bug.

## Same mix bug again, one level down: ring archetypes
**When:** day 3, splitting device and address sharing into three ring archetypes
**Symptom:** target archetype mix was 40% tight / 35% dropship / 25% household. Measured over ring *accounts* it came out 42 / 46 / 12. Household, the archetype that produces the address-sharing-without-device-sharing pattern the whole change exists to create, was at less than half its intended weight.
**Root cause:** a recurrence of the day-1 class, not a new bug. The archetype was chosen once per cluster with `random.choices(weights=(0.40, 0.35, 0.25))`, but a cluster contributes 3-6 accounts, so the draw controls the mix of *clusters* and not the mix of *accounts*. With roughly twenty clusters in the pool, ordinary sampling variance in cluster sizes was enough to swing an archetype by more than a factor of two. Day 1 was the identical mistake at persona level; I re-introduced it at archetype level in the same file, nine days later, having already written it up.
**Fix:** allocate by target account count, the same shape as the persona fix — loop the archetypes, mint clusters until each one's account target is reached. Then added the assert that should have existed from the start: pin each archetype's observed account share to its target within 0.10.
**Result:** 43 / 30 / 27. Residual drift is structural, since clusters are minted whole and the last one can overshoot by up to five accounts, and the 0.10 tolerance accommodates it. Checked against the failing run: household at 0.122 is 0.128 off target, so the new assert would have fired.
**Caught by:** manual inspection, not the harness. The persona-mix assert from day 1 was passing the whole time and had nothing to say about archetypes. The lesson is not "I made the mistake twice" but that writing a failure up does not prevent it — only an assert does, and the day-1 fix stopped one level too high.

## A calibration correction that measured well and did not survive a real holdout
**When:** day 3, after training the first calibrated model
**Symptom:** none. Nothing crashed and no assert fired. The decile table on a 70/30 holdout showed the model claiming 0.602 in the bucket sitting on the fight/refund boundary and delivering 0.456, a gap of -0.146 across 90 alerts, plus a smaller -0.068 gap in the top decile. Reported both as findings and built a correction that mapped every raw prediction through the observed rate for its bucket, with a weighted isotonic pass to stop the noisier buckets inverting the ranking.
**Root cause:** the gap was sampling noise, and the correction was fitted on the same 900 rows it was evaluated on, so it scored perfectly by construction and could not be caught. A decile of a 900-row holdout is 90 alerts; at p≈0.5 that carries a 95% interval of about ±0.10, and the -0.146 sat inside it. The deeper mistake was structural rather than statistical: with only train and test, anything fitted after training has nowhere honest to be measured, so a correction that learns the holdout's noise looks free.
**Fix:** resplit 60/20/20 into train / calibration / test. Model fitted on train, model selection and the correction fitted on calibration, everything reported on test. Then measured the same prediction band on every slice: calibration +0.027 (n=62, ±0.123), test -0.109 (n=60, ±0.126), train -0.008 (n=167, ±0.075), pooled -0.040 (n=122, ±0.089). Two independent slices disagreed in sign, and the largest and most precise estimate said the model was already calibrated at the boundary. Applying the correction cost -0.0017 AUC and +0.0005 Brier on rows it had not seen. Removed it from `predict_win_prob`, which now returns the raw isotonic-calibrated probability.
**Result:** `build_correction` and the decile table stay in the file as reporting only, and `calibration.md` publishes the raw-versus-corrected comparison so the rejection is visible rather than merely asserted. A self-check now fails if `predict_win_prob` ever returns bucketed values again. Side benefit of removing it: P(win) is continuous again instead of nine discrete steps with a hole between 0.246 and 0.583, which would have straddled any EV threshold `policy.py` picks.
**Caught by:** measurement, once the measurement was built honestly. This was not a bug -- every line did what it was written to do. It was a claim that looked supported at the sample size available and was not, and it took a third split to find that out. The same caution now applies to the other number in `calibration.md`: dropping customer-supplied features "costs approximately nothing", and that sentence is the claim, not the fourth decimal underneath it.

## The review harness reported zero verdicts while appearing to run
**When:** day 5, adversarially reviewing llm.py before committing it
**Symptom:** a four-lens attack-then-refute workflow completed "successfully" and returned `{"confirmed": [], "split": [], "total_raised": 0}` — which read as a clean bill of health for freshly written failure-handling code. It was nothing of the sort. The four attack agents had run and raised 16 findings; the entire verification stage had silently produced zero verdicts.
**Root cause:** the orchestration script fed `parallel()` an array of already-invoked promises — `parallel([agent(...), agent(...)])` — where it requires thunks: `parallel([() => agent(...), ...])`. Each inner call failed, each enclosing task resolved to null, and the final `.filter(Boolean)` swept the wreckage away, so the aggregate arithmetic ran happily over an empty list. The failures were recorded in diagnostics I had to go looking for; the headline result looked like success.
**Fix:** none to the harness mid-flight — the attack results were already journaled, so I read the 16 raw findings directly and verified them by hand instead of re-running. Acceptance criterion: a finding was believed only if it carried an executed demonstration (stubbed client raising OverflowError, the ₹21,000/P(win)=0.20 alert flipping refund→fight on the contradiction flag alone), not on the reviewer-agent's say-so. Nine were real and got fixed; the rest were by-design behaviour or theoretical.
**Result:** the fixes landed in the same commit as llm.py, so no false claim ever reached the repo — but only because the empty result looked suspicious enough to check the diagnostics rather than being taken at face value.
**Caught by:** reading the failure diagnostics attached to a "completed" run, not by the harness itself. Same class as the calibration correction entry above: silent success is worse than loud failure. The correction scored perfectly because it was graded on its own training data; the review scored clean because its graders never ran. Both times the system said "fine" through a mechanism that could not have said anything else, and both times the defence was distrusting a result that arrived too easily. A verification stage that can produce zero verdicts without erroring is itself unverified.
